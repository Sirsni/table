# HANDOFF.md — передаточный документ проекта

*Написано Fable 5 (дирижёр проекта) для Opus, Sonnet и владельца. Здесь то, что
нельзя увидеть в коде: выстраданные факты о Steam, состояние проекта, идеи и
дорожная карта. Прочитай целиком, прежде чем что-то менять.*

---

## 1. Что это за проект (одним абзацем)

Таблица сравнения цен Steam Market (аналог Tradeback/vvtable): монорепо
TypeScript (shared / collector / server / web), SQLite, React+TanStack Table.
Собирает цены и историю продаж, считает **реальную** маржу перепродажи и ищет
выгодные предметы. Дальше по плану: внешние площадки (loot.farm, market.csgo,
Skinport...), межплощадочный арбитраж, затем торговый бот. Полный план — PLAN.md.

## 2. Выстраданные факты о Steam (НЕ переоткрывай их заново)

Это главная ценность документа. Каждый пункт стоил часов отладки:

1. **Новый рынок Steam (React/SSR, ~2026)**: на странице предмета БОЛЬШЕ НЕТ
   `Market_LoadOrderSpread(item_nameid)`. Стакан берётся по ИМЕНИ:
   `GET /market/orderbook?q=Load&qp=[appid,"market_hash_name"]`
   → `{ success, data: { amtMaxBuyOrder, amtMinSellOrder, eCurrency, cBuyOrders, cSellOrders } }`
   (цены в минимальных единицах). item_nameid не нужен вовсе.
2. **Валюта orderbook определяется гео выходного IP** и параметр `currency` в
   query ИГНОРИРУЕТСЯ. У владельца VPN через Польшу → eCurrency=6 (PLN). Поэтому
   в БД хранится валюта каждого снапшота, а сервер конвертирует в USD (fx.ts,
   open.er-api.com, офлайн-кэш). Не «чини» это выставлением параметра — не работает.
3. **Квота, а не rate limit**: ~**1000 запросов на IP за окно (~30 мин)**, потом
   429 на всё, бан ~15+ минут. Скорость НЕ влияет (проверено: 1 req/s банит на
   той же ~1000-й). Отсюда: предохранитель 429 (8 подряд → авто-стоп), быстрый
   отказ на 429 вместо длинных ретраев. Полный каталог одним IP за раз недостижим —
   проходы возобновляемые (сортировка по давности обновления).
4. **`search/render` глубже ~первых страниц отдаёт пустые results (200, items=[])**,
   особенно под параллельной нагрузкой; total_count=33671 недостижим. Поэтому sync
   идёт ПОСЛЕДОВАТЕЛЬНО и останавливается после 5 пустых страниц подряд. За
   несколько запусков накоплено ~9k предметов CS2 (upsert склеивает).
   Чтобы добрать каталог: перебирать `sort_column` (price/name/quantity) ×
   `sort_dir` и фильтры категорий — каждый срез открывает другие предметы. НЕ
   реализовано, хорошая следующая задача.
5. **`pricehistory` требует cookie** (`steamLoginSecure` залогиненного аккаунта,
   env STEAM_COOKIE в .env в корне). Отдаёт ВСЮ историю: за последний месяц —
   почасовые точки, старше — дневные. Формат: `[["Jul 14 2023 01: +0", 12.34, "57"], ...]`
   (дата, медиана-цена float, qty строкой). ВАЖНО: живьём формат ещё НЕ проверен
   (владелец переустанавливал Windows) — есть кнопка «Проверить cookie»
   (GET /api/cookie/check), начни проверку с неё. Если формат другой — попроси
   у владельца сырой JSON (инструкция: открыть URL pricehistory в браузере под
   вторым аккаунтом, Ctrl+A, Ctrl+C).
6. **Steam блокирует датацентровые IP (403)** — из облачного контейнера Claude
   запросы не работают. Проверяй код синтетикой (fake http + DB_PATH=/tmp) и
   selftest'ами; живые прогоны делает владелец на своём ПК.
7. **Сеть владельца**: РФ, ТСПУ, у провайдера CGNAT (прямой IP часто в бане).
   Работает через Happ (VLESS Reality) в режиме «туннель для выбранных
   приложений» — **node.exe должен быть в списке** приложений Happ. Windows
   резолвит localhost в ::1 → везде используем 127.0.0.1 явно (vite host/proxy,
   сервер). Windows cmd: `&&` не работает в старом PowerShell — команды по одной.
8. **Node 22, НЕ 24**: better-sqlite3 не имеет prebuilt-бинарника под Node 24 →
   node-gyp/Python-ад. package.json engines >=22; у владельца стоит 22 LTS.
9. **Зависшие соединения тоннеля**: у undici-fetch НЕТ таймаута по умолчанию —
   без AbortSignal.timeout (20с, STEAM_TIMEOUT_MS) воркеры замерзали намертво.
   Не убирай таймаут.
10. **Комиссия Steam**: продавец получает `base`, где gross = base +
    max(1, floor(base*0.05)) + max(1, floor(base*0.10)). Инверсия — подбором
    (sellerReceives в shared/economics.ts, проверено против реального Steam
    до цента: $1000 → $869.58). Не заменяй на «gross/1.15».

## 3. Состояние проекта (что готово / что не проверено живьём)

Готово и проверено живьём владельцем:
- sync каталога (последовательный, с ранним стопом), обновление цен (orderbook,
  пул воркеров, скорость из UI), USD-конвертация, веб-таблица с сортировкой,
  фильтрами, парой сервисов «Купить на / Продать на» (STEAM / STEAM(AUTO)),
  панель сбора с прогрессом/стопом, предохранитель 429, мгновенный «Стоп».

Готово в коде, НО НЕ проверено живьём (нужен рабочий STEAM_COOKIE):
- pricehistory → item_stats (sales7d/30d, VWAP, медианы, p25, волатильность,
  baseline/recent, boostScore) + сырые точки в price_points (35 дней);
- реальная маржа по медиане (realProfitUsd/realMarginPct), детектор буста
  (boostSuspect: score>=1.5 или лот>=1.5×медианы при sales30d>=5), фильтры
  minRealMargin/hideBoost, бейдж «⚠ буст».
Первый шаг следующей сессии: владелец жмёт «Проверить cookie», потом
«Обновить историю» — и проверить, что колонки заполнились и медианы совпадают
с реальностью (см. §2 п.5 про формат).

Инфраструктура: ветка `claude/ecstatic-bardeen-elgcwp`; данные в `<корень>/data/`
(SQLite, WAL, пути от корня репо — НЕ от cwd); .env в корне (STEAM_COOKIE,
опц. STEAM_PROXY/STEAM_INTERVAL_MS/STEAM_CONCURRENCY/STEAM_TIMEOUT_MS/DB_PATH/
FX_CACHE_PATH/PORT); `npm run dev` = сервер 127.0.0.1:3000 + vite 127.0.0.1:5173.

## 4. Алгоритмы: что уже есть и КАК ДУМАТЬ о следующих

Ключевая рамка: **прибыль = f(цена входа, реальная цена выхода, вероятность
исполнения, время оборота, риск)**. Сейчас реализованы первые два члена.
Дальше — по убыванию ценности:

### 4.1 Вероятность исполнения автозапроса (fill rate) — СЛЕДУЮЩИЙ АЛГОРИТМ
Автозапрос исполняется, когда кто-то продаёт «в бид». По price_points посчитать:
`fillVolume30d = сумма qty точек с price <= buyOrder*1.02` — сколько раз за месяц
продавали по цене ≤ твоего бида. Это прямая оценка «сколько штук/мес я реально
откуплю». Ожидаемая прибыль/мес = fillVolume30d × realProfit. Сортировка по ней —
сильнейший ранкер таблицы. Данные УЖЕ в БД (price_points), нужен только расчёт
на сервере (points подгружать по id, как item_stats).

### 4.2 Время оборота
turnoverDays ≈ (лоты на продажу cSellOrders) / (продажи в день sales30d/30) —
сколько дней очередь из текущих лотов рассасывается. Если >14 — капитал виснет.
Фильтр «макс. дней оборота». Всё для расчёта уже в БД.

### 4.3 Детектор буста v2 (сейчас v1: recent/baseline медианы)
Известный нюанс v1: realMargin берёт median_7d ?? median_30d, а во время буста
median_7d уже задрана — забустенный предмет может показать высокую «реальную»
маржу И метку буста одновременно. Фичи задуманы в связке (сначала hideBoost,
потом маржа), но лучше усилить: при boostSuspect брать консервативную оценку
продажи (baseline_price или median_30d) вместо median_7d.
Улучшения по мере данных:
- z-score последних сделок против распределения 30д (устойчивее порога 1.5);
- объёмный сигнал: всплеск покупок ПЕРЕД ростом цены (скупили стакан) — по
  часовым точкам виден как пик qty при старой цене;
- «тонкий стакан»: cSellOrders аномально мал против типичного (нужно копить
  историю снапшотов cSellOrders — данные уже пишутся в price_snapshots.volume);
- обратный сигнал (dump detection) — резкий провал = возможность купить.

### 4.4 Бэктест — козырь, которого нет у конкурентов
В price_points лежит месяц почасовых сделок. Можно ПРОВЕРИТЬ стратегию на
истории: «если бы я месяц держал бид на уровне p10 и продавал по медиане —
сколько бы заработал на этом предмете?» Симулятор ~100 строк: для каждого
предмета пройтись по точкам, исполнение бида = точка с ценой ниже бида,
продажа = следующая точка ~медианной цены. Выход — годовая доходность на
предмет. Это отделяет фантомную маржу от реальной лучше любых эвристик.

### 4.5 Межплощадочный арбитраж (этап 4 PLAN.md) — где настоящие деньги
Начать с loot.farm: ПУБЛИЧНЫЙ `https://loot.farm/fullprice.json` — весь прайс
одним запросом, без ключей и банов. Дальше market.csgo (API по ключу), Skinport,
CSFloat. Интерфейс MarketProvider уже в shared. Сравнение: купить Steam
(автозапрос/лот) → продать на площадке X и наоборот, с комиссиями обеих сторон.
ВАЖНО: деньги в Steam — «фантики»; реальный кэшаут только через площадки, поэтому
Steam→X — главный маршрут. Маппинг имён: у всех market_hash_name, но проверяй
износы/StatTrak/сувениры краевыми случаями.

### 4.6 Масштабирование сбора
- Bulk-цены продажи: search/render УЖЕ отдаёт sell_price+sell_listings на 100
  предметов за 1 запрос — сейчас выбрасываются (пишем только имя/иконку).
  Записывать их как снапшоты → весь каталог «продажных» цен за ~20 запросов.
  Дорогим остаётся только автозапрос (1 запрос/предмет) — тянуть его только по
  вотчлисту/кандидатам, прошедшим фильтры.
- Пул прокси: резидентные/мобильные (датацентровые Steam режет, см. §2 п.6).
  Каждый IP = своя квота ~1000. Раунд-робин в SteamHttp (dispatcher на запрос).
- Приоритизация: ликвидное — часто, неликвид — раз в сутки. listItemsFor*Update
  уже сортируют по давности; добавить вес по sales30d.

### 4.7 Идеи UI
- Мини-графики (sparkline) из price_points прямо в строке — данные уже есть,
  эндпоинт GET /api/items/:id/points + canvas/svg.
- Вотчлист (звёздочка, отдельная таблица с частым обновлением).
- Пресеты фильтров («ликвидный арбитраж», «охота за дипами», «без бустов»).

### 4.8 Бот (этап 5) — только после стабильной аналитики
Node-стек DoctorMcKay: steam-user, steam-tradeoffer-manager, steam-totp.
ОТДЕЛЬНЫЙ аккаунт, dry-run режим обязателен, лимит капитала, kill-switch, журнал
операций. Покупка: POST /market/buylisting (нужны sessionid cookie), выставление:
/market/sellitem. И помни про trade hold 7 дней на новых устройствах.

## 5. Правила работы, которые себя оправдали

- **Дирижёр планирует и ревьюит, исполнители пишут**: спека с точными формулами,
  контрактами API и краевыми случаями → coder-opus (логика) / coder-sonnet
  (UI/рутина) → ревью кода дирижёром → сборка/синтетика → коммит цельного среза.
  Файлы агентов: .claude/agents/coder-opus.md, coder-sonnet.md.
- Каждое изменение: `npm run build` + `npm run typecheck` + selftest'ы
  (economics.selftest.ts, stats.selftest.ts) + синтетический прогон на
  DB_PATH=/tmp с fake-http. Коммитить только собирающиеся срезы.
- Владелец — не программист: инструкции — конкретные команды по одной, без
  жаргона; просить полный вывод консоли, НЕ игнорировать ошибки; скриншоты ок.
  Cookie и секреты в чат не просить никогда (.env, он в .gitignore).
- Steam-эндпоинты изолированы в collector/src/steam/* — при изменениях Steam
  чинить только там. Все цены в БД — integer в минимальных единицах + код валюты.
- НЕ запускать `npm audit fix --force` (сломает vite/fastify мажорами).

## 6. Приоритеты следующих сессий (моя рекомендация)

1. Проверить живьём pricehistory (кнопка «Проверить cookie») и наполнить историю.
2. Fill rate (§4.1) + время оборота (§4.2) — превращают таблицу в ранкер
   реальной ожидаемой прибыли. Дёшево: данные уже в БД.
3. Bulk-цены из search/render (§4.6) — свежесть всего каталога почти бесплатно.
4. loot.farm провайдер (§4.5) — первый межплощадочный арбитраж за один вечер.
5. Спарклайны из price_points — «вау» и практично.
6. Пул прокси — когда упрётесь в квоту всерьёз.
7. Бэктест (§4.4) — перед тем как доверять деньгам, и обязательно перед ботом.

Удачи. Проект в хорошей форме: архитектура тянет и площадки, и бота; главное —
не терять дисциплину «спека → код → синтетика → живая проверка владельцем».
