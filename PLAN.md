# План разработки: таблица сравнения цен Steam Market (аналог Tradeback.io / vvtable)

## 1. Что строим

Сервис, который:

1. **Этап 1 (MVP):** парсит торговую площадку Steam (CS2, Dota 2, Rust) и считает
   спред внутри Steam: «автозапрос на покупку → обычная продажа» с учётом комиссии (~13%).
2. **Этап 2:** показывает результаты в виде таблицы с фильтрами/сортировкой (веб-интерфейс,
   работает локально на твоём ПК, позже разворачивается как сайт без переделки).
3. **Этап 3:** подключает внешние площадки (loot.farm, cs.money, market.csgo, Skinport и т.д.)
   и сравнивает цены между площадками.
4. **Этап 4:** торговый бот, который сам выставляет ордера / принимает трейды.

## 2. Выбор языка и стека

**Рекомендация: TypeScript / Node.js на всём проекте.** Почему:

- Лучшие в мире библиотеки для Steam-ботов написаны под Node.js — экосистема DoctorMcKay:
  `steam-user`, `steam-tradeoffer-manager`, `steam-totp`, `steamcommunity`. Аналоги на
  Python (steampy) заметно слабее и хуже поддерживаются. Раз бот в планах — это решающий аргумент.
- Один язык на парсер, API, фронтенд и бота: не надо переключаться между экосистемами.
- Парсинг — это в основном асинхронные HTTP-запросы с rate-limit'ом, Node для этого идеален.

Альтернатива: Python (FastAPI) для парсера + React-фронт. Проще для старта, но на этапе
бота всё равно придётся брать Node — получится зоопарк из двух языков.

**Стек:**

| Слой | Технология |
|---|---|
| Сборщик цен (worker) | Node.js + TypeScript, `got`/`axios`, очередь с rate-limit (`p-queue`) |
| База данных | SQLite (через `better-sqlite3` или Prisma) → PostgreSQL при переходе в веб |
| API | Fastify (или Next.js API routes) |
| Фронтенд | React + Vite, таблица — TanStack Table (сортировка/фильтры из коробки) |
| Бот (позже) | `steam-user` + `steam-tradeoffer-manager` + `steam-totp` |

**Почему веб-интерфейс, а не десктоп-программа:** интерфейс сразу делаем как локальный
сайт (`http://localhost:3000`). На твоём ПК это просто `npm run dev`, а «веб-версия в будущем»
— это тот же код, задеплоенный на VPS. Ноль переделок.

## 4. Как парсить Steam (технические детали)

App ID: **CS2 = 730, Dota 2 = 570, Rust = 252490**.

Эндпоинты (неофициальные, но стабильные годами):

1. **Список предметов** —
   `https://steamcommunity.com/market/search/render/?appid=730&norender=1&count=100&start=N`
   Пагинация по всем предметам игры: имя, минимальная цена продажи, число лотов.
2. **item_nameid** — числовой ID предмета для стакана заявок. Берётся один раз со страницы
   предмета (`/market/listings/730/<market_hash_name>`, regex по `Market_LoadOrderSpread(ID)`)
   и **кешируется навсегда** в БД — он не меняется.
3. **Стакан (то, что нам нужно для автозапроса)** —
   `https://steamcommunity.com/market/itemordershistogram?country=RU&language=russian&currency=5&item_nameid=<ID>`
   Возвращает `highest_buy_order` (автозапрос) и `lowest_sell_order` (мгновенная продажа),
   плюс графики заявок.
4. (опционально) `priceoverview` — медианная цена и объём за сутки для фильтра ликвидности.

**Экономика спреда** (комиссия Steam для CS2/Dota/Rust ≈ 5% Steam + 10% игре):

```
выручка_продавца ≈ цена_продажи / 1.15          (Steam округляет, точную формулу зашить в код)
прибыль          = выручка_продавца − цена_автозапроса
маржа %          = прибыль / цена_автозапроса × 100
```

В таблице показываем: предмет, автозапрос, мин. цена продажи, прибыль ₽, маржа %, объём/сутки.

**Главное ограничение — rate limit Steam:** без авторизации ~20 запросов/мин с одного IP,
дальше HTTP 429 и временный бан IP. Стратегия:

- Очередь с throttle ~1 запрос / 3 сек на IP (`p-queue` с interval).
- Кеш `item_nameid` (самая дорогая часть — нужна 1 раз на предмет).
- Обновлять предметы по приоритету: ликвидные чаще, неликвид раз в часы.
- На вырост: пул прокси для ускорения (каждый прокси = свой лимит).
- Полный проход по ~2000 ликвидным предметам CS2 займёт ~1.5–2 часа на одном IP —
  это нормально для старта, фильтр по объёму сократит список.

## 5. Схема БД (минимум)

```sql
items(id, app_id, market_hash_name, item_nameid, icon_url, updated_at)
price_snapshots(id, item_id, provider, buy_order, sell_price, volume, fetched_at)
```

## 6. Этапы разработки

### Этап 0 — каркас (1 вечер)
- Монорепо (npm workspaces), TypeScript, ESLint, структура пакетов, SQLite.

### Этап 1 — парсер Steam, CS2 (ядро проекта)
- Клиент `search/render` → загрузка списка предметов CS2 в БД.
- Резолвер `item_nameid` с кешем.
- Опрос `itemordershistogram` через очередь с rate-limit, запись snapshot'ов.
- Расчёт прибыли/маржи. Обработка 429 (экспоненциальная пауза), ретраи, логи.
- Проверка: консольный вывод топ-20 предметов по марже.

### Этап 2 — таблица (веб)
- Fastify API: `GET /api/items?app=730&minMargin=5&minVolume=20&sort=margin`.
- React + TanStack Table: фильтры (игра, цена от/до, маржа %, объём), сортировка,
  поиск по названию, автообновление, ссылка на предмет в Steam.
- Запуск: `npm run dev` → открыл `localhost:3000`.

### Этап 3 — Dota 2 и Rust
- Те же эндпоинты, просто appid 570 и 252490 + переключатель игры в UI.
- Здесь же: история цен (данные уже копятся в snapshots) и мини-графики.

### Этап 4 — внешние площадки
- Реализация `MarketProvider` для каждой:
  - **loot.farm** — публичный JSON `https://loot.farm/fullprice.json` (самый простой, с него начать);
  - **market.csgo (TM)** — официальное API по ключу;
  - **Skinport / CSFloat** — публичные API;
  - **cs.money** — официального API нет, парсинг внутренних эндпоинтов (хрупко, оставить напоследок).
- Маппинг названий предметов между площадками (у всех `market_hash_name`, но есть нюансы).
- Режим таблицы «Steam ↔ площадка X»: где купить, где продать, профит с учётом комиссий обеих сторон.

### Этап 5 — торговый бот
- Отдельный **новый аккаунт Steam** (не основной!), мобильный аутентификатор,
  `shared_secret`/`identity_secret` для `steam-totp`.
- `steam-user` — логин и сессия; `steam-tradeoffer-manager` — приём/отправка трейдов;
  покупка на ТП — авторизованные запросы к `market/buylisting`, выставление лотов — `market/sellitem`.
- Логика: следить за спредом → перебивать автозапрос → при покупке выставлять на продажу.
- Обязательно: лимиты на сумму в работе, kill-switch, журнал всех операций, симуляция (dry-run) до реальных денег.

## 7. Риски и ограничения (важно знать заранее)

- **ToS Steam:** автоматизация покупок/продаж на ТП формально запрещена подпиской Steam.
  На практике боты массово существуют, но риск ограничений аккаунта есть — поэтому бот
  только на отдельном аккаунте и с консервативными лимитами запросов.
- **Rate limit** — главный технический враг; архитектура выше построена вокруг него.
- **Trade hold / Market hold:** новые аккаунты и предметы имеют задержки (7 дней trade hold
  без мобильного аутентификатора и т.п.) — влияет на скорость оборота бота.
- **Неофициальные эндпоинты** могут поменяться — изолировать их в одном модуле.
- Цены в Steam — в «фантиках» кошелька: маржа внутри Steam не равна выводу реальных денег.
  Реальный кэшаут — это как раз этап 4 (продажа на внешних площадках).
