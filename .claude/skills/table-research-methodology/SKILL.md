# Методология исследования

Не использовать для: известных симптомов (→ table-debugging-playbook), хроники (→ table-failure-archaeology).

## Эталонный кейс: сага синхронизации (коммиты 9e2ce23 → e39ce8d → cd239c3)
Симптом: sync останавливается на случайном числе, ошибок ноль. Г1 «скорость/параллельность» — опровергнута: 1 req/s даёт то же (предсказание не сбылось). Г2 «пропуск offset» — реальный баг (лог владельца: 55 страниц × ~10 = 540), исправлен, но симптом ОСТАЛСЯ → Г2 не объясняла всё. Ключевой ход: перестали гадать, добавили ЛОГ СЫРЫХ ТЕЛ (data/sync-debug.log) → заглушка `{success:true,total_count:0,results:[]}` объяснила РАЗОМ все наблюдения: «нет ошибок» (это 200), «случайное число» (момент включения заглушки), «ровно после ~30 запросов» (период троттла), и почему паузы «не работали» (total_count=0 обходил их же условие).

## Правила, выведенные из практики
1. Гипотеза обязана предсказывать ЧИСЛО до эксперимента («если квота — бан на ~1000-м независимо от скорости»). Не сбылось — гипотеза мертва, не «почти подтвердилась».
2. Одно объяснение должно покрывать ВСЕ симптомы, включая отрицательные («ошибок нет» — тоже симптом). Частично объясняющий фикс = не конец расследования.
3. Прежде чем чинить — добудь сырые данные (тела ответов, точные числа из логов владельца: ×70 = курс рубля; 540 = 54×10). Дешёвый разграничивающий эксперимент — первым.
4. Синтетическое воспроизведение обязательно (fake http + DB_PATH=/tmp): фикс без воспроизводящего теста не принимается. Примеры: заглушка (700/700), предохранитель (стоп 8/200), отмена (151мс vs 2000мс).
5. Живая проверка владельцем закрывает цикл; результат — запись в table-failure-archaeology и HANDOFF.md.
6. Адверсариальная проверка: перед принятием вывода попроси агента ОПРОВЕРГНУТЬ его.

## Жизненный цикл идеи
Кандидат (table-research-frontier) → кампания с гейтами → table-change-control → принято ИЛИ задокументированный отказ (в архeологию — отвергнутые пути тоже знание).
