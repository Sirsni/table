## 1. Классы изменений и их гейты

«Гейт» = обязательная проверка, без прохождения которой коммитить нельзя.
Базовые команды гейтов (из корня репо, все проверены исполнением):

```bash
npm run build        # порядок: shared -> collector -> server -> web (корневой package.json)
npm run typecheck    # tsc --noEmit по всем workspace'ам
npx tsx packages/shared/src/economics.selftest.ts     # «economics.selftest: OK»
npx tsx packages/collector/src/stats.selftest.ts      # «stats.selftest: OK»
```

«Синтетика» = прогон реального кода на временной БД с поддельным HTTP, без
Steam (из контейнера Steam всё равно отдаёт 403 датацентровым IP). Паттерн:
fake-объект `{ concurrency, hasCookie, getJson, getText }` вместо SteamHttp +
`openDb("/tmp/x.sqlite")` из `packages/collector/dist/db.js`. Рабочий образец —
`scripts/null-visibility-check.mjs` в этом каталоге. Интерфейс SteamHttp:
`packages/collector/src/steam/http.ts` (getJson/getText/concurrency/hasCookie).

«Живая проверка» = владелец на своём Windows-ПК прогоняет фичу против живого
Steam и присылает полный вывод/скриншот. Обязательна для всего, что трогает
Steam или данные: код может быть идеально типизирован и всё равно врать о
поведении Steam (см. table-validation-and-qa про протокол).

## 2. Общий порядок для любого изменения

1. Классифицируй изменение по таблице §1 (может попасть в 2 класса — гейты складываются).
2. Прогони гейты. Падение любого = изменение не готово, чинить, не «обходить».
3. Для метрик/фильтров — обязательный §3 (доктрина).
4. Коммит цельного среза в ветку `claude/ecstatic-bardeen-elgcwp` (§4, §5).
5. Всё, что касается Steam/данных, — в очередь на живую проверку владельцем;
   в HANDOFF.md/ответе явно пометь «не проверено живьём», пока он не подтвердил.

## 3. ДОКТРИНА ЛОЖНООТРИЦАТЕЛЬНЫХ (правило №1 владельца)

**Не отсекать прибыльные предметы по ошибке или непроверенному предположению.**
Ложноотрицательный (прибыльный предмет спрятан) хуже ложноположительного
(мусор показан): спрятанную прибыль никто никогда не увидит и не узнает о потере,
а показанный мусор виден и проверяется глазами. Следствие: **лучше показать
подозрительный предмет с меткой, чем скрыть**.

### Живая ловушка в текущем коде (проверена исполнением)

Цепочка, из-за которой предмет может «исчезнуть» без единой ошибки в логике:

1. `fetchPriceHistory` БРОСАЕТ на пустой истории: `packages/collector/src/steam/pricehistory.ts`
   строка ~122 — `prices.length === 0` → throw «пустая история».
2. `enrichHistory` ловит это как обычный fail предмета (runner.ts, catch в worker)
   → `upsertItemStats` НЕ вызывается → строки в item_stats нет.
3. В `queryItems` у такого предмета `sales30d = null` (items.ts:331), и фильтр
   `minSales30d` отбрасывает null: items.ts:366
   `dtos.filter((d) => d.sales30d !== null && d.sales30d >= min)`.

Итог: предмет, у которого просто не было продаж за месяц (или история не
загрузилась из-за сбоя), навсегда невидим при включённом фильтре ликвидности.
Доказательство — прогон `scripts/null-visibility-check.mjs` (выход 1, предмет
«No-History Case» скрыт). Статус: **известный компромисс** — minSales* это
явный opt-in фильтр ликвидности, но при изменениях вокруг item_stats помни,
что «нет строки» и «0 продаж» сейчас неразличимы. Идея писать нулевую
статистику вместо fail — **открыто/кандидат**, решает дирижёр+владелец.

### Эталонные паттерны в коде (делай так)

| Паттерн | Где | Суть |
|---|---|---|
| null не считается виной | items.ts:379-382 (`hideBoost`) | Отбрасывается только `boostSuspect === true`; null/false остаются. Проверено: script с `{"hideBoost":true}` показывает оба предмета |
| null в конец, но виден | items.ts:421-426 (сортировка) | null-значения уходят в конец списка при любом направлении — не скрываются |
| метка вместо скрытия | boostSuspect/boostScore как колонка | Подозрение на буст ПОКАЗЫВАЕТСЯ (бейдж/колонка), скрытие — только явным hideBoost |
| кламп вместо фильтра | items.ts:265-296 (realSell) | Сомнительная цена продажи не выкидывает предмет, а консервативно ограничивается min(лот, свежая медиана) |

Осознанные базовые отсечки (не трогай молча, но знай о них): view `items_latest`
— INNER JOIN со снапшотами (db.ts, VIEW_SQL) — предмет без единого снапшота цен
невидим; `WHERE buy_order IS NOT NULL AND sell_price IS NOT NULL` (items.ts:159-163)
— без обеих цен маржу не посчитать. Это дефицит ДАННЫХ, лечится сбором, а не кодом.

### Чек-лист для нового фильтра/метрики (обязателен)

- [ ] Политика null решена ЯВНО и записана комментарием у фильтра: показывать
      (как hideBoost) / скрывать (как minSales30d — тогда почему это ок?).
- [ ] Прогнан `node .claude/skills/table-change-control/scripts/null-visibility-check.mjs '{"твойФильтр":X}'`
      (нужен свежий `npm run build`). Exit 1 = скрывает предметы без данных —
      требуется явное обоснование в коммите.
- [ ] Проверка на известно-прибыльном кейсе: обвалившийся предмет (свежая медиана
      много ниже старой — кейс Cologne 2026 из коммита 751bb4e) НЕ должен ни
      исчезнуть, ни показать фантомную маржу. Рецепты синтетических историй —
      table-analysis-toolkit.
- [ ] Если метрика «подозрительности» — она добавляет МЕТКУ/колонку, а скрытие
      делается отдельным opt-in фильтром с дефолтом «выключено».
- [ ] stats.selftest расширен кейсами новой метрики (пустая история, одна точка,
      все точки старше окна).

## 4. Непреложные правила (каждое оплачено инцидентом или решением владельца)

1. **Только ветка `claude/ecstatic-bardeen-elgcwp`, PR не создавать.** Решение
   владельца; все 36+ коммитов проекта в ней (`git log --oneline`). Git-команды,
   меняющие состояние вне коммита в эту ветку (push в другие ветки, rebase main,
   создание PR) — нет.
2. **`npm audit fix --force` ЗАПРЕЩЁН.** Он поднимет vite ^5 / fastify ^5
   мажорами и сломает сборку (HANDOFF §5). Уязвимости dev-зависимостей локального
   инструмента — не повод ломать рабочий проект. Обновление мажоров — только
   как отдельная задача с полными гейтами класса «Зависимости».
3. **Секреты — только .env, НИКОГДА не просить в чат.** STEAM_COOKIE
   (steamLoginSecure) и любые ключи живут в `.env` в корне (он в .gitignore —
   проверено), грузятся через `node --env-file-if-exists=../../.env` в скриптах
   workspace'ов. Владельцу говорить «положи в .env», не «пришли мне». Детали
   env — table-config-and-env.
4. **Деньги владельца и риск бана — только после явного «да».** Покупка
   прокси/подписок/ключей, агрессивные скорости сбора (риск 429-бана IP:
   квота ~1000 запросов/IP за ~30 мин, независимо от скорости — steam-market-reference),
   любые реальные сделки будущего бота — сначала предупреждение с описанием
   риска, потом ожидание согласия. Бот до явного разрешения — только dry-run.
5. **Цены в БД — только integer в минимальных единицах + код валюты.** Все
   ценовые колонки (buy_order, sell_price, median_*, price, ...) — INTEGER,
   рядом колонка currency (Steam eCurrency): см. db.ts CREATE TABLE. Причина:
   комиссия Steam считается floor'ами на целых копейках
   (`gross = base + max(1,floor(base*0.05)) + max(1,floor(base*0.10))`,
   shared/src/economics.ts), float-цены дают расхождение с реальным Steam.
   Инверсия — подбором, проверено до цента: `sellerReceives(100000) === 86958`
   ($1000 → $869.58). Конвертация в USD — на сервере при чтении (fx.ts), а не
   при записи.
6. **Node 22, не 24** (engines >=22; better-sqlite3 без prebuilt под 24) и
   прочие грабли среды — одна строка здесь, полностью в table-config-and-env.

## 5. Паттерн разработки: спека → агент → ревью → синтетика → цельный коммит

Проверенный процесс (HANDOFF §5, файлы агентов существуют в `.claude/agents/`):

1. **Дирижёр пишет спеку**: точные формулы, контракты API, краевые случаи.
   Архитектура и публичные интерфейсы фиксируются В спеке.
2. **Исполнитель пишет код**: `coder-opus` (сложная логика: retry-стратегии,
   парсинг, алгоритмы) или `coder-sonnet` (рутина по чёткому ТЗ: boilerplate,
   эндпоинты, конфиги). Оба обязаны: не менять границы модулей, сообщать о
   дырах в ТЗ, прогонять компиляцию. См. `.claude/agents/coder-opus.md`,
   `coder-sonnet.md`.
3. **Ревью дирижёром**: сверка с спекой + доктрина §3 + запреты §1/§4.
4. **Гейты** класса изменения (§1) + синтетика.
5. **Коммит цельного среза**: одно изменение = один собирающийся коммит со
   всеми затронутыми слоями (пример: 6ca289f — stats + items + web разом).
   Что писать в сообщение коммита — table-docs-and-writing.
6. **Живая проверка владельцем** — до неё фича «не проверено живьём» (так и
   помечать в HANDOFF.md).

Steam-эндпоинты изолированы в `packages/collector/src/steam/*` — при изменениях
поведения Steam чинить только там, не размазывая знание о Steam по слоям.
