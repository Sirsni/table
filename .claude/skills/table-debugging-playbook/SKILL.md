# table-debugging-playbook — симптом → триаж → фикс

Ранбук отладки. Формат: увидел симптом — найди строку в мастер-таблице — выполни
разграничивающий эксперимент (эксперимент, чей результат однозначно разделяет
конкурирующие причины) — примени фикс. НЕ гадай и не «чини» вслепую: главный
провал проекта («остановка синхронизации», 3 итерации неверных гипотез) случился
именно из-за починки по предположению вместо чтения сырых улик.

Этот скилл — про «сломалось/висит/пусто/явно не то». Про «работает, но, кажется,
считает неоптимально» — analysis-toolkit и research-frontier.

## Шаг 0: собери улики, прежде чем думать

Источники улик (все проверены по коду 2026-07-09):

| Улика | Где | Что содержит |
|---|---|---|
| `[steam] GET <url> -> <status>` | консоль сервера (в dev — строки с префиксом `[server]` от concurrently) | каждый HTTP-запрос к Steam и его статус; warn при 403/429/5xx/сетевых (`packages/collector/src/steam/http.ts`) |
| `[sync] ...` | там же | пустые страницы, паузы тихого троттлинга, счётчик «пустых подряд» (`packages/collector/src/runner.ts`) |
| `[search] ...` | там же | success=false / битые страницы search/render (`searchRender.ts`) |
| `[enrich] ...` | там же | одноразовое предупреждение «история в валюте кошелька» (`runner.ts`) |
| `[collector] <kind>: остановлено: <причина> — обработано X/Y, ok=, fail=` | там же | ЧЕМ закончилась каждая задача — читай эту строку первой (`packages/server/src/collectorService.ts`, finish) |
| `data/sync-debug.log` | корень репо | СЫРЫЕ тела пустых/битых ответов search/render: строки `<ISO> start=<N> EMPTY|BAD|NOT_JSON body=<до 800 симв.>` (`searchRender.ts`) |
| `GET /api/collector/status` | `curl.exe http://127.0.0.1:3000/api/collector/status` | running/kind/processed/total/ok/fail/lastName/lastError — lastError содержит stoppedReason |
| Панель сбора в вебе | строка «Ошибка: ...» | тот же lastError (`packages/web/src/CollectorPanel.tsx`) |

Что просить у владельца (он не программист, инструкции — по одной команде):
- ПОЛНЫЙ вывод консоли с момента запуска, не фрагмент «где ошибка». Скриншот ок.
- Хвост debug-лога: `Get-Content data\sync-debug.log -Tail 30` (PowerShell, из корня репо).
- Статус коллектора: `curl.exe http://127.0.0.1:3000/api/collector/status` (именно
  `curl.exe`: голый `curl` в PowerShell — алиас Invoke-WebRequest с другим выводом).
- НИКОГДА не просить STEAM_COOKIE или его значение в чат — только «проверь, что
  он в .env» и кнопка «Проверить cookie».
- Версию Node при проблемах сборки/установки: `node -v`.

## §1. Разбор: sync останавливается «сам по себе» (самый болезненный кейс)

Симптом: синхронизация каталога завершается на случайной глубине, ошибок нет.
Стоил 3 итераций неверных гипотез (полная хроника — table-failure-archaeology,
методические выводы — table-research-methodology). Краткая история:

1. **9e2ce23** (2026-07-07): search/render ИГНОРИРУЕТ count=100, реально ~10
   предметов/страницу, а цикл двигал offset на 100 → пропуск 90% каталога и
   «случайный стоп». Фикс: offset двигается на фактически полученное.
2. **e39ce8d** (2026-07-07): «тихий троттлинг» — глубже некоторой глубины Steam
   отдаёт 200 с пустыми results (не 429!). Фикс: паузы и повтор ТОГО ЖЕ offset.
3. **cd239c3** (2026-07-07): лог владельца показал заглушку целиком:
   `{success:true, total_count:0, results:[]}` — total_count=0 одновременно
   обходил условие повтора И срабатывал как «достигли total_count». Фикс:
   total_count доверяем ТОЛЬКО из непустых страниц (knownTotal) + каждый
   пустой/битый ответ пишется сырым в `data/sync-debug.log`.

Текущее поведение (`runner.ts`, syncItems) — знай, что НОРМА, а что нет:

| Наблюдение | Вердикт |
|---|---|
| `[sync] пустая страница start=N ... тихий троттлинг ... пауза 0.5с и повтор (1/5)` | НОРМА. Заглушка приходит примерно раз в ~30 запросов и обычно снимается с первого повтора. Паузы: 0.5/1.5/5/15/30с (emptyRetryWaits) |
| Строки `EMPTY body={"success":true,"total_count":0,...}` в sync-debug.log | НОРМА — это та самая заглушка, механизм её пережидает |
| `[sync] offset N пуст после всех повторов (пустых подряд: K/5)` | Троттлинг не прошёл после всех пауз; после 5 таких offset'ов подряд (STOP_AFTER_EMPTY=5) — авто-стоп с внятным stoppedReason |
| `[collector] sync: остановлено: Steam перестал отдавать страницы каталога...` | Штатный ранний стоп. Собранное сохранено (upsert), перезапуск позже добирает дальше |
| `[collector] sync: остановлено: Steam вернул 429...` | Предохранитель квоты (8 подряд 429) → строка 2 мастер-таблицы |
| Стоп БЕЗ строки `[collector]` вообще | Процесс сервера умер — читать `[server]` строки выше по логу, это уже другой отказ |

Порядок триажа: (1) строка `[collector] sync: ...` — вердикт задачи;
(2) хвост `data/sync-debug.log` — что фактически отвечал Steam;
(3) только потом гипотезы. Тела ответов уже записаны — читать, не угадывать.

## §3. Правила триажа (несгибаемые)

1. **Улики раньше гипотез.** Сырые тела уже пишутся в sync-debug.log, вердикты —
   в `[collector]`-строку. Урок кейса §1: две итерации потрачены на правдоподобные
   гипотезы, победила та, что пришла из фактического лога владельца.
2. **Доктрина ложноотрицательных** (см. table-change-control): фикс не имеет
   права молча ПРЯТАТЬ предметы. Чинишь странные цифры — предмет остаётся видимым
   с меткой, а не исчезает из выдачи.
3. **429 = ждать, а не крутить ручки.** Квота на IP, скорость не влияет.
4. **Не убирать предохранители**: таймаут запроса (п.9), предохранитель 429,
   паузы тихого троттлинга — каждый закрывает реальный прошлый отказ.
5. **Секреты не трогаем**: cookie не просить, не логировать (http.ts значение
   cookie не логирует — сохраняй это свойство в любых фиксах).
6. Фикс → `npm run build` + `npm run typecheck` + selftest'ы + синтетика → коммит
   в `claude/ecstatic-bardeen-elgcwp` → живая проверка владельцем
   (протокол — table-validation-and-qa).
